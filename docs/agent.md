# Ai-Sistem — главные правила проекта

## 1. Назначение

Ai-Sistem — независимая универсальная AI Development System для управления разработкой и экспертной проверкой цифровых продуктов.

Telegram является первым пользовательским интерфейсом системы. Система не привязана к LifeGame и должна поддерживать несколько независимых проектов.

LifeGame является отдельным продуктом, подключаемым к Ai-Sistem через контролируемые интерфейсы и интеграции.

## 2. Архитектурный принцип

Ai-Sistem и проекты, которыми она управляет, должны оставаться независимыми.

Нельзя проектировать Ai-Sistem так, чтобы её внутренняя логика зависела от конкретной структуры LifeGame.

Концептуальная модель:

Ai-Sistem → Project → Repository / Services / Data

Один экземпляр Ai-Sistem должен иметь возможность работать с несколькими проектами.

## 3. Экспертная система

В Ai-Sistem предусмотрены следующие роли:

1. Главный эксперт / Coordinator — определяет, какие эксперты необходимы для задачи, организует workflow и контролирует выполнение.
2. Финансовый эксперт — финансовая методология.
3. Исторический эксперт — исторические данные и источники.
4. Эксперт-разработчик — код, архитектура и техническая реализация.
5. Научный эксперт — научная валидация.
6. UX Product Expert — качество продукта с точки зрения пользователя.
7. Security Expert — безопасность проекта.
8. Data Statistics Expert — статистика и анализ данных.
9. Экономический эксперт — экономическая теория.

Эксперт отвечает только в пределах своей зоны компетенции.

## 4. Coordinator

Coordinator не заменяет предметных экспертов.

Его задача:
- понять запрос;
- определить проект;
- определить необходимых экспертов;
- назначить основной и консультирующие роли;
- организовать согласование;
- контролировать состояние задачи;
- собрать итог;
- передать результат пользователю.

Coordinator не должен самостоятельно выдавать экспертное заключение там, где требуется специализированный эксперт.

## 5. Границы ответственности

Ни один агент не должен самостоятельно выполнять действия вне своей зоны ответственности.

Эксперт может давать рекомендации другому эксперту, но не получает автоматически его полномочия.

Изменение исходного кода выполняется Экспертом-разработчиком после получения необходимых согласований.

Критические изменения безопасности требуют участия Security Expert.

## 6. Работа с проектами

Каждая задача должна быть связана с конкретным project.

Контекст разных проектов нельзя смешивать.

Память, решения, документы, задачи и данные проекта должны иметь явную принадлежность к project.

LifeGame не является внутренним модулем Ai-Sistem.

## 7. Context Packet

Каждый вызов AI должен получать явно сформированный контекст, соответствующий его роли и проекту.

Минимальная структура:

```
Platform
Project
Agent
Task
Project Knowledge
Execution Rules
```

Для эксперта Agent содержит:
- key;
- role;
- persistent instructions.

Project содержит только разрешённый контекст проекта.

Task содержит пользовательский запрос и конкретную задачу эксперта.

Execution Rules определяют ограничения, работу с фактами, предположениями и неопределённостью.

AI не должен самостоятельно угадывать проект, роль или полномочия.

## 8. Безопасность Context Packet

Context Packet не может содержать:
- API keys;
- service-role/secret keys;
- Telegram bot tokens;
- webhook secrets;
- пароли;
- другие секреты инфраструктуры.

AI не получает произвольный доступ к GitHub, Supabase или production-данным.

Инструкции агентов загружаются runtime только по разрешённому пути из конфигурации агента.

Контекст разных проектов не смешивается.

## 9. Telegram

Telegram — интерфейс управления и наблюдения за системой.

На первом этапе допускается один технический Telegram Bot.

Различные эксперты могут иметь собственные имена, аватары и визуальные идентификаторы в Telegram, оставаясь отдельными AI-агентами внутри общей системы.

Telegram не должен содержать основную бизнес-логику системы.

## 10. Данные и безопасность

Данные Ai-Sistem и данные управляемых продуктов должны быть логически разделены.

Ai-Sistem не должна получать неограниченный доступ к production-данным проектов.

Доступ к внешним системам предоставляется по принципу минимально необходимых полномочий.

Все чувствительные операции должны быть контролируемыми и по возможности журналироваться.

## 11. Supabase

Ai-Sistem использует отдельный Supabase-проект.

Supabase Ai-Sistem хранит данные самой системы: проекты, агентов, задачи, workflow, память, решения, разрешения и аудит.

Supabase LifeGame остаётся отдельным.

Взаимодействие между ними выполняется через контролируемые API, сервисные интеграции или другие явно определённые интерфейсы.

## 12. GitHub и изменения

Все изменения должны быть воспроизводимыми и понятными.

Перед изменением существующего файла необходимо учитывать его текущую версию и содержимое.

Каждый изменённый или созданный файл должен иметь маркер версии в верхней части, если формат файла это позволяет.

Формат:

# version 1.0

При последующем изменении версия увеличивается: 1.1, 1.2 и т.д.

## 13. Структура файлов

Имена новых файлов и каталогов должны быть в lowercase.

Один файл должен иметь одну основную ответственность.

Не следует создавать монолитные файлы, объединяющие независимые функции.

## 14. Документация изменений

Изменения проекта фиксируются в docs/changes/.

Для каждой даты создаётся отдельный каталог:

docs/changes/DD.MM.YYYY/

В журнале указываются:
- дата и время по Москве;
- изменённые файлы;
- что изменено;
- причина изменения;
- статус согласования.

## 15. Процесс работы

Если пользователь формулирует задачу:
1. Coordinator определяет контекст и проект.
2. Определяются необходимые эксперты.
3. При необходимости проводится экспертное согласование.
4. Создаётся план реализации.
5. Изменения выполняются только после необходимого согласования.
6. Результат проверяется.
7. Итог и статус сообщаются пользователю.
8. Изменения фиксируются в журнале.

## 16. Принцип достоверности

Нельзя выдавать предположение за установленный факт.

Если эксперт не располагает достаточными данными, он должен явно сообщить об ограничении и запросить необходимые данные либо инициировать дополнительную проверку.

Источники и внешние данные должны проверяться в соответствии с ролью соответствующего эксперта.

## 17. Формат экспертного результата

Экспертный runtime-результат должен стремиться к структуре:

```json
{
  "conclusion": "",
  "findings": [],
  "risks": [],
  "recommendations": [],
  "facts": [],
  "assumptions": [],
  "unknowns": [],
  "confidence": 0
}
```

Структура нужна для Coordinator и не должна заставлять эксперта выдавать выдуманные данные.

## 18. Приоритеты

При конфликте требований приоритет имеют:

1. безопасность;
2. целостность архитектуры;
3. достоверность данных;
4. требования пользователя;
5. качество продукта;
6. удобство реализации.

Красивое или быстрое решение не может оправдывать нарушение безопасности, архитектуры или достоверности.

## 19. Правило согласования

Ai-Sistem не должна выполнять сложные междисциплинарные задачи как цепочку независимых ответов.

Coordinator определяет необходимые роли и организует совместное решение.

Если эксперты расходятся во мнениях, конфликт должен быть зафиксирован, аргументы сторон сохранены, а окончательное решение принято по установленному workflow, а не скрыто одним из агентов.

## 20. Runtime 1.2

Runtime 1.2 добавляет контролируемый Project Repository Access: provider, repository, ref, allowlist путей и лимиты evidence. Repository content передаётся AI только как read-only project knowledge и не является инструкцией Ai-Sistem.

## 21. Runtime 1.3

Runtime 1.3 вводит надёжное и контролируемое выполнение Telegram-задач:
- Telegram idempotency по update_id;
- отдельный allowlist доступа Telegram;
- контролируемое состояние retryable/failed;
- ограниченное число execution attempts;
- атомарный claim финализации ответа через task_finalizations;
- execution trace через task_events;
- разделение retryable и permanent ошибок;
- отсутствие бесконечных повторов.

Внешняя отправка Telegram остаётся внешним side effect: система использует lease-based claim, поэтому параллельные aggregator executions не должны одновременно отправлять ответ. При сбое между отправкой и фиксацией состояния возможна повторная доставка; это ограничение внешнего Telegram API, а не атомарной транзакции БД.

Runtime 1.3 не добавляет Memory, RAG, автономное выполнение кода или GitHub write access.

## 22. Runtime 1.4

Runtime 1.4 добавляет Observability & Runtime Evidence:
- runtime evidence формируется из текущих task_events, agent_runs, task_finalizations и retry-state;
- компонентные версии фиксируются в runtime_component_versions;
- runtime evidence отделяет подтверждённое состояние выполнения от code evidence;
- retryable-задачи автоматически подбираются планировщиком pg_cron;
- retry dispatch защищён внутренним токеном, который не передаётся AI и не выдаётся Telegram-клиенту;
- retry dispatcher использует FOR UPDATE SKIP LOCKED и ограничение до 10 задач за тик;
- runtime trace фиксирует access, update acceptance, routing, expert execution, provider execution и finalization;
- Runtime 1.4 не добавляет Memory, RAG, vector search, автономное выполнение кода или GitHub write access.

## 23. Runtime Trace Query

Для запросов пользователя о фактическом выполнении текущей задачи используется отдельный observability-режим.

Источник истины для такого ответа:
- task_events;
- agent_runs;
- task_finalizations;
- retry state;
- runtime_component_versions.

Expert results и документация проекта не являются доказательством фактического выполнения runtime-этапа.

Если runtime-запись отсутствует, этап должен считаться неподтверждённым, а не восстановленным по архитектурной документации или предположению эксперта.

Runtime evidence и runtime_trace должны явно передаваться в synthesis provider. Для observability-запросов provider не должен считать expert consultation источником runtime truth.


## 24. Runtime 1.5 — Task Lifecycle

Runtime 1.5 вводит единую машину состояний задачи:

```
pending → consulting → synthesizing → completed
                    ↘ retryable
retryable → pending
```

Дополнительные терминальные состояния: `failed`, `blocked`, `cancelled`.

Правила:
- `tasks.status` является единственным источником текущего lifecycle state;
- переходы контролируются на уровне PostgreSQL trigger;
- `consulting` означает выполнение экспертных консультаций;
- `synthesizing` означает выполнение итогового synthesis/finalization этапа;
- `completed` выставляется только после успешной финализации ответа;
- `retryable` используется для контролируемого восстановления;
- завершённые состояния нельзя переводить обратно в активные;
- Runtime 1.5 не добавляет Memory, RAG, автономное выполнение кода или GitHub write access.

## 25. Runtime 1.5 — Recovery & Delivery Evidence

Runtime 1.5 дополнительно обеспечивает восстановление зависших задач и подтверждаемую доставку Telegram-ответа.

Recovery:
- `pending` старше 2 минут считается зависшим;
- `consulting` старше 10 минут считается зависшим;
- `synthesizing` старше 5 минут считается зависшим;
- зависшая задача переводится в `retryable` с ограничением `max_attempts`;
- recovery выполняется отдельным pg_cron job.

Delivery Evidence:
- Telegram `sendMessage` должен вернуть успешный API response и `message_id`;
- message IDs и подтверждение Telegram API сохраняются в `task_finalizations`;
- завершение task и фиксация delivery evidence выполняются одной PostgreSQL-функцией;
- Telegram остаётся внешним side effect, поэтому абсолютный exactly-once delivery не гарантируется при crash между внешней отправкой и DB commit.

## 26. Runtime Trace API

`runtime-trace` — read-only внутренний Edge API для получения authoritative runtime snapshot конкретной задачи.

Контракт:
- POST с `task_id`;
- доступ только по service-role authorization;
- только UUID task_id;
- не изменяет задачи, события, runs или delivery state;
- источник истины: `tasks`, `task_events`, `agent_runs`, `task_finalizations`, `telegram_updates`, `runtime_component_versions`;
- возвращает lifecycle, runtime stages, agent runs, retries, Telegram delivery evidence и активные runtime versions;
- экспертные ответы, документация и code evidence не считаются runtime evidence.

`runtime-trace` не предоставляет публичный пользовательский доступ. Telegram/Admin UI должны обращаться к нему через доверенный backend-контур.

## 28. Token Efficiency & Context Budget

Цель стандарта — минимизировать необоснованный расход токенов, не снижая качество, точность и безопасность экспертного результата. Экономия достигается маршрутизацией, отбором контекста, ограничением повторов и измерением фактического потребления, а не механическим урезанием критически важных данных.

### 28.1. Минимально достаточная экспертиза

- Coordinator выбирает минимальный достаточный набор экспертов для конкретной задачи.
- Все девять ролей не запускаются по умолчанию. Дополнительный эксперт назначается, когда его компетенция необходима для достоверного результата или снижения существенного риска.
- Простые задачи по возможности направляются одному профильному эксперту.
- Междисциплинарные, архитектурные и критичные с точки зрения безопасности задачи получают расширенный состав согласно обоснованной необходимости.
- Решение о составе экспертов и причинах расширения состава должно быть доступно в runtime evidence.

### 28.2. Контекст по принципу минимально необходимых данных

- Каждый вызов получает только контекст, необходимый для своей роли, задачи и выбранного проекта.
- Не передавать полную историю диалога, все документы проекта или полный репозиторий, если достаточно релевантной выдержки.
- Инструкции агента, описание проекта, пользовательский запрос, evidence и результаты других экспертов не должны дублироваться без необходимости.
- Репозиторные evidence выбираются по релевантности задаче и allowlist. Количество файлов и размер каждого файла являются верхними техническими пределами, а не целевым объёмом передачи модели.
- До вызова провайдера следует применять лимиты размера контекста и проверять оценку токенов. Подсчёт символов или байтов не считается точным подсчётом токенов.
- Контекст можно сокращать только с сохранением важных фактов, ограничений, доказательств, решений и неопределённостей. При невозможности безопасного сокращения вызов должен быть остановлен или переведён на контролируемый путь обработки.

### 28.3. Бюджет на нескольких уровнях

Расход контролируется отдельно для:
1. отдельного provider-вызова;
2. одного запуска агента;
3. всей задачи, включая все экспертные консультации, повторы и финальный синтез;
4. параллельных вызовов системы относительно доступного лимита провайдера.

Для каждого уровня должны быть определены входной бюджет, выходной бюджет, максимальное количество попыток и поведение при превышении лимита. Числовые значения устанавливаются конфигурацией и подтверждаются измерениями на тестовых задачах; они не должны объявляться универсальными до проверки модели, её контекстного окна и тарифных ограничений.

Ограничение max_output_tokens регулирует выходную генерацию и само по себе не ограничивает входной контекст, суммарный расход задачи или TPM.

### 28.4. Приоритеты расходования

- В первую очередь сохраняются корректность, безопасность, существенные evidence и требования пользователя.
- Затем сокращаются повторы, нерелевантные документы, дублирующиеся инструкции, избыточные промежуточные результаты и необязательные экспертные вызовы.
- Структурированные результаты экспертов передаются Coordinator в компактном виде с сохранением выводов, ключевых фактов, рисков, рекомендаций и неизвестных.
- Coordinator не должен повторно запускать уже успешно выполненную экспертизу без изменения входных данных или явно установленной причины.
- Недостаточная длина ответа сама по себе не является основанием для повторного вызова. Повтор допускается, если результат пустой, повреждённый, не соответствует обязательному контракту или не покрывает существенное требование задачи.

### 28.5. Повторы, параллелизм и rate limits

- Повторы ограничиваются общим бюджетом задачи и max_attempts; бесконечные и скрытые повторы запрещены.
- Ошибки классифицируются как временные, постоянные, quota/billing-related, rate-limit-related или ошибки контракта. Классификация должна опираться на ответ провайдера, а не только на HTTP-код.
- При наличии Retry-After система соблюдает его в пределах установленной политики. Она не должна многократно немедленно повторять запрос, когда провайдер сообщает о длительном ограничении.
- Параллельные экспертные вызовы ограничиваются общим диспетчером/бюджетом, чтобы суммарная нагрузка не исчерпывала TPM из-за одновременного старта.
- Перед повторной отправкой нужно проверить состояние существующего agent_run, чтобы не создавать дубликат уже завершённой или выполняющейся работы.
- При исчерпании бюджета задача останавливается в контролируемом состоянии, причина записывается в runtime events, пользователю возвращается понятное сообщение. Необязательные вызовы не запускаются.

### 28.6. Измерение фактического потребления

Для каждого provider-вызова необходимо сохранять, если данные доступны от API:
- provider и фактически использованную модель;
- режим вызова (expert или synthesis);
- входные, выходные и общие токены согласно usage-метаданным ответа;
- оценку входных токенов до запроса, если она используется;
- task_id, agent_run_id, номер попытки и длительность;
- статус, класс ошибки и причину повтора;
- применённый бюджет и факт его превышения.

Фактические usage-данные провайдера отделяются от локальных оценок. Если провайдер не вернул точное значение, поле остаётся неизвестным; оценка не выдаётся за фактический расход. Секреты, полный API key и чувствительный содержательный контекст не должны попадать в журнал.

Отчётность должна отдельно показывать:
- токены, использованные в успешных вызовах;
- неуспешные попытки, если провайдер предоставляет их usage;
- суммарный расход на задачу;
- расход по экспертам и synthesis;
- количество вызовов и повторов;
- оценки и фактические значения раздельно.

### 28.7. Качество и валидация

- Бюджет не должен принуждать эксперта пропускать критически важные риски или выдумывать недостающие сведения.
- Если контекста недостаточно, агент фиксирует неизвестные и запрашивает необходимые данные либо сообщает об ограничении.
- После сокращения контекста сохраняется обязательный контракт результата, включая факты, предположения, риски, рекомендации и неизвестные.
- Изменения токен-бюджетов проверяются на наборах простых, междисциплинарных и сложных задач. Сравниваются качество, полнота, число вызовов, входные/выходные токены, повторы и итоговая стоимость.
- Уменьшение расхода не считается успешным, если оно ухудшает корректность, безопасность или полноту критически важных выводов.

### 28.8. Начальный аудит текущей реализации

На момент фиксации стандарта в коде обнаружены следующие факты:
- `coordinator-worker` использует keyword-router для выбора профильных экспертов; это уже позволяет не запускать все роли на каждый запрос, но качество и полнота маршрутизации требуют тестирования.
- `expert-worker` загружает настроенные repository evidence и передаёт их каждому выбранному эксперту. В конфигурации есть предел числа файлов и байтов на файл, но это не является токен-бюджетом; файл размером до 200 000 байт потенциально может создать очень большой контекст.
- `expert-worker` диспетчеризует созданные экспертные запуски через `Promise.all`, поэтому отдельные вызовы могут стартовать параллельно без видимого в этой функции общего token/TPM-бюджета.
- `ai-provider-worker` ограничивает выход до 3 000 токенов для эксперта и до 4 000 для synthesis, но в проверенной реализации не обнаружено сохранения usage-метрик ответа провайдера. Эти лимиты не защищают от чрезмерного входного контекста.
- `result-aggregator` сокращает отдельные поля результатов экспертов и repository evidence перед synthesis, однако это ограничение по символам, а не по токенам; полный итоговый контекст всё ещё нуждается в бюджетировании.
- В коде по умолчанию задана модель `gpt-6-luna`. До подтверждения фактического `OPENAI_MODEL` и поддержки модели нельзя считать модельную конфигурацию проверенной.

Эти пункты являются code audit evidence, а не подтверждением того, сколько токенов реально было использовано в предыдущих запросах. Для установления фактического расхода необходимы usage-метаданные провайдера и/или сохранённые runtime-логи.

### 28.9. Статус внедрения

Этот раздел фиксирует обязательные архитектурные правила и выявленные направления технической работы. Само добавление документации не включает runtime-лимиты и не меняет поведение Edge Functions. Реализация должна выполняться отдельными согласованными изменениями с тестами и проверкой регрессий.
